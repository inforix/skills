# 写作和质量规范

## 信息架构

按用户任务组织内容，不按源码目录罗列。区分教程、操作指南、参考和解释；不同受众可共用概述，但用户操作、管理员运维和开发者 API 应清晰分区。

## 写作规则

- 首段先说明读者能完成什么；步骤用编号列表，每步只放一个主要动作。
- 先说明操作位置，再说明动作；命令后给出预期结果和恢复方式。
- 每一个操作都必须交代目的、前置条件、操作位置、动作、预期结果和失败恢复；关键操作尽量配与步骤绑定的真实截图。
- UI 名称、配置键、命令、错误文本与截图必须与证据一致。
- 截图辅助定位和确认状态；关键内容必须在正文中也能获得。每图有题注、具体替代文本和对应步骤 ID。
- 使用中性、直接、可翻译的语言；缩写首次出现时解释，全篇术语一致。
- 示例使用安全占位数据，禁止真实凭据、个人信息或内部敏感地址。
- Markdown 标题只使用 1–3 级并映射为 Word Heading 1–3；不要用加粗正文伪造标题。
- 表格仅用于真正的行列数据，列表必须使用真实编号结构。

## 证据等级

1. 运行态验证：实际页面、命令或响应已验证。
2. 结构化契约：OpenAPI、类型声明、配置 schema、测试可直接证明。
3. 源码证据：实现或路由可证明，但未做运行验证。
4. 现有文档：需与当前代码版本交叉核对。
5. 推测：只能进入待确认清单，不能进入事实性正文。

发生冲突时优先使用更新且更接近运行态的证据，并在整合报告中记录取舍。

## 双格式一致性

- Word 与单文件 HTML 使用同一配置、Markdown 章节、API 数据和截图 manifest。
- 两份成品的软件名、版本、章节顺序、步骤、参数、错误码、截图与未验证声明必须一致。
- Word 保证可编辑、分页稳定、目录和页眉页脚正确；HTML 保证无 CDN、可搜索、可打印、可离线阅读。
- 有 UI 时必须启动应用并采集真实截图；HTTP 200、空页面、错误页或旧图不算截图验收。

## 质量评分

每项 0–25 分，总分 100：完整性、准确性、可执行性、交付可用性。

阻断错误包括：虚构功能、秘密泄露、操作步骤缺少必要说明、关键操作没有截图且未说明原因、截图与正文不一致、有 UI 却未尝试启动和截图、DOCX 无法打开、逐页渲染存在截断/重叠、HTML 无法离线打开、双格式事实不一致。存在阻断错误时不得宣称完成。

最终至少满足：无阻断错误、总分不低于 80、所有未验证项显式列出。发布级手册目标分数为 90，并完成应用运行、截图、DOCX 逐页渲染和 HTML 浏览器验收。
