# 运行与认证流程

本流程用于有 UI 的软件手册。运行时验证能证明手册描述的是当前应用，而不是仅由源码或端口状态推断出的功能。

## 1. 盘点运行拓扑

从 `package.json`、`pyproject.toml`、`docker-compose*.yml`、Makefile、README、开发脚本和测试配置中识别：

- 前端/后端开发服务器及其启动命令、工作目录、健康路由和目标业务路由；
- 必需的数据库、缓存、消息队列、对象存储、搜索服务、worker、浏览器自动化服务等依赖；
- 认证入口、回调地址、测试账号约定和需要用户人工完成的步骤。

不要凭服务名称猜测依赖。只有被启动命令、配置或运行错误证明为必要的组件才纳入本次启动范围。

## 2. 安全启动

1. 记录当前分支、工作区状态、目标工作目录和启动命令。
2. 检查目标端口和进程。已在运行且归属不明的服务视为共享服务，不接管、不重启、不停止。
3. 先启动缺失的依赖组件，再启动应用；优先使用仓库已有脚本和已安装依赖，不安装包、不修改 `.env`、锁文件、认证逻辑、数据库结构或种子数据。
4. 为本次启动的每个进程记录 PID、命令、日志位置、监听地址和就绪信号。就绪信号应是健康检查、日志中的 ready 标记或可访问的业务端点，而不是只有端口开放。
5. 应用或依赖启动失败时，基于日志做最多两次有限修正重试；缺少私有配置、外部服务或权限时停止尝试并转为部分完成，不索取秘密。

## 3. 浏览器人工认证

当目标路由跳转到登录页、显示 SSO、MFA、验证码或其他需要真人输入的认证界面时：

1. 使用可用的浏览器控制能力打开登录入口，并把浏览器置于用户可操作状态。
2. 明确告诉用户“请直接在浏览器中完成认证，完成后回复我”；不要要求用户在聊天中发送用户名、密码、验证码、恢复码或令牌。
3. 不通过脚本、键盘自动化、剪贴板、环境变量、开发者工具或网络日志代填或读取认证材料。不要截图或写出含认证材料的页面状态。
4. 等待用户完成认证。用户回复完成后，或浏览器已显示已登录的目标业务状态时，再验证一个非敏感的业务信号，例如目标路由可访问、登录入口变为用户菜单、核心控件出现或受保护 API 返回正常业务结果。
5. 若认证未完成、会话过期或页面仍停留在登录/错误/空白状态，继续停留在认证门禁，不伪造成功，不采集占位截图。必要时生成 `screenshots/MANUAL_CAPTURE.md`，标记为部分完成。

## 4. 运行证据

在工作目录中写入 `runtime/runtime-manifest.json`，至少记录：

```json
{
  "status": "verified|partial|blocked",
  "services": [{"name": "app", "command": "...", "pid": 123, "url": "...", "ready_signal": "..."}],
  "auth": {"required": true, "status": "user_completed|not_required|blocked", "secret_values_recorded": false},
  "business_checks": [{"route": "/example", "status": "passed", "evidence": "visible control: ..."}]
}
```

命令、URL、路由和可见控件可以记录；密码、验证码、令牌、Cookie、完整个人信息和敏感响应体不得记录。手册只引用已通过业务检查的运行证据。

## 5. 收尾

完成截图和业务检查后，只停止本流程启动且 PID 仍与记录一致的进程。共享数据库、缓存、对象存储和其他既有服务保持运行。若用户要求保留开发服务，记录这一事实，不擅自停止。
